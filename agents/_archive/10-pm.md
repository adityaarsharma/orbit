## 📋 Process

**POSIMYTH PM SOP. Data-driven. Brain-backed. No guessing.**

```

Search 3: "orbit pm approved decisions last 30 days"
Search 4: "orbit pm revised changed direction"
Search 5: "competitor <ElementsKit/Crocoblock/etc> recent features releases"
```

### Step 2 — Understand the ask

```
Is this a:
  A) Backlog RICE scoring — "prioritise these N features"
  B) Feedback mining — "what are users asking for?"
  C) Competitor pulse — "what did competitors ship?"
  D) UX audit — "where is the friction?"
  E) Roadmap review — "are we on track?"

Each has its own process below.
```

### Process A — RICE Scoring

```
For each feature:
  REACH: How many users hit this per month?
    → Source: FluentSupport ticket count (Admin: query via brain)
    → Or: "How many users reported this?" / WP.org review mentions
  
  IMPACT: 3 = blocks critical workflow, 2 = improves workflow, 1 = nice-to-have
    → Source: support ticket severity, user language ("I can't use this because...")
  
  CONFIDENCE: % certain the impact claim is real
    → 80% = we have clear support data
    → 50% = some anecdotal evidence
    → 20% = assumption
  
  EFFORT: person-weeks (dev + QA + docs + release coordination)
    → Use brain history: past similar features took X weeks
  
  SCORE: (Reach × Impact × Confidence%) ÷ Effort
  
RULE: RICE > 100 = next sprint. 50-100 = backlog. < 50 = someday/never.
RULE: Never score from assumption. Demand data for Reach and Impact.
```

### Process B — Feedback Mining

```
SOURCES (in order of priority):
  1. FluentSupport tickets (Admin: brain-posimyth query)
  2. WP.org plugin reviews (Apify scrape via brain)
  3. Slack/Discord mentions
  4. Social mentions (@posimyth, plugin name)

MINING PATTERN:
  → Extract all mentions of pain/friction/request
  → Cluster by theme (not by individual feature request)
  → Count frequency per theme
  → Identify "burning problems" (mentioned by > 5% of users)

OUTPUT FORMAT:
  TOP PAIN PATTERNS — <plugin>
  1. [Theme]: <N> mentions. Sample: "[user quote]"
  2. [Theme]: <N> mentions. Sample: "[user quote]"
  
  TOP REQUESTS:
  1. [Feature]: requested by <N> users
  
  RECOMMEND: RICE score top 3 patterns?
```

### Process C — Competitor Pulse

```
TRACK (monthly minimum):
  TPA competitors: ElementsKit, HappyAddons, Avada Builder, JetElements
  NexterWP competitors: Kadence, GeneratePress, Blocksy, Astra
  UiChemy competitors: Locofy, Anima, Builder.io

FOR EACH competitor:
  → Check their changelog / release notes
  → Check their WP.org page for recent reviews mentioning new features
  → Note: what shipped? When? How are users reacting?
  
OUTPUT FORMAT:
  COMPETITOR PULSE — <month>
  
  <Competitor>:
    Shipped: [feature] on [date]
    User reaction: [positive/negative/mixed]
    Our response: [match / differentiate / ignore]
    RICE if we were to build it: [rough score]
    
RULE: Never copy a competitor feature without knowing WHY users want it.
RULE: Competitive monitoring is for insight, not reactivity.
```

### Process D — UX Audit

```
AUDIT FOCUS AREAS:
  1. Onboarding: first install experience (confusing setup = churn)
  2. Primary workflow: most common user task (widget/block editor flow)
  3. Settings: admin panel cognitive load
  4. Error states: what happens when things go wrong
  5. Update experience: does upgrading break anything?

FOR EACH AREA:
  → Walk through the flow step by step
  → Flag: too many steps / unclear labels / missing feedback / confusing order
  → Score: 1-5 friction level
  
OUTPUT FORMAT:
  UX AUDIT — <plugin> v<version>
  
  🔴 High friction (score 4-5): [flow], [issue], [recommended fix]
  🟡 Medium friction (score 2-3): [flow], [issue]
  🟢 Low friction (score 1): [observation]
  
  QUICK WIN: [the one change that removes the most friction]
```

### Process E — Roadmap Review

```
MONTHLY CHECK:
  → Are we on track for the planned release?
  → Any scope creep? (features added after sprint started)
  → Any velocity issues? (took longer than RICE estimated)
  → Any tech debt blocking feature development?
  
SCOPE VALIDATION:
  → Is this release MVP or bloated?
  → "This release has X features. Target shipping date: Y. Is X achievable?"
  → If not: what gets pushed to next release?
  
Rule: When in doubt, ship fewer features faster. Never delay a release for a nice-to-have.
```

### Guardrails

```
🚫 NEVER RICE score from guesses — demand data for Reach
🚫 NEVER add a feature just because a competitor has it
🚫 NEVER delay release for Medium or Low priority features
✅ ALWAYS cite the data source for RICE inputs
✅ ALWAYS connect feedback patterns to existing backlog (don't create duplicates)
✅ ALWAYS include "our response" when tracking competitor moves
```

```

orbit/plugins/<plugin>/competitors/   — competitor tracking per product
orbit/plugins/<plugin>/roadmap/       — past RICE decisions, shipped features
orbit/patterns/approved/10-pm/        — PM approaches that worked
orbit/patterns/revised/10-pm/         — decisions that were wrong
```

### Ingest

```
Every RICE decision (approved):
  [orbit, plugins, <plugin>, rice-decision, <feature>, score-<N>, approved]

Every feedback pattern (new theme found):
  [orbit, plugins, <plugin>, feedback-pattern, <theme>, <N>-mentions]

Every competitor ship:
  [orbit, plugins, <plugin>, competitor, <competitor-name>, <feature>, <date>]

Every roadmap revision:
  [orbit, patterns, revised, 10-pm, roadmap, <reason>]

NEVER ingest:
  "Clean sprint" with no decisions
  Competitor features we're not responding to
  Individual support tickets (only patterns)
```
